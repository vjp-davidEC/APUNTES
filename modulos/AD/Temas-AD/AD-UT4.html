Mapeo Objeto-Relacional: Arquitectura y Configuración con Hibernate y JPA

1. Introducción y Concepto de Mapeo Objeto-Relacional (ORM)

El Desfase Objeto-Relacional: Hace referencia a la diferencia en el tratamiento de la información entre una aplicación orientada a objetos (que trabaja con instancias de clases y sus relaciones) y una base de datos relacional (que opera con tablas, relaciones y conjuntos). Para leer o escribir información entre ambos paradigmas se requiere un proceso de adaptación continuo.

Definición de ORM: El Mapeo Objeto-Relacional es una técnica de programación que convierte datos entre el sistema de tipos de un lenguaje orientado a objetos y el de una base de datos relacional mediante un motor de persistencia. En la práctica, crea una base de datos orientada a objetos virtual que actúa de interfaz intermedia.

Esquema Conceptual del Mapeo Objeto-Relacional
[ Objetos (Aplicación OO) ] <===> [ Motor de Persistencia (ORM) ] <===> [ Tablas (SGBDR) ]
Código Comparativo: Mapeo Manual Tradicional con JDBC
public List<Alumno> findAll() throws ClassNotFoundException, SQLException {
    String sql = "SELECT ID_ALUMNO, NOMBRE, APELLIDOS, "
               + "TO_CHAR(FECHA_NACIMIENTO, 'DD/MM/YYYY') AS FEC_NAC, "
               + "CORREO_ELECTRONICO, HORAS_FALTAS FROM ALUM";
    List<Alumno> result = null;
    
    PreparedStatement ps = DBConnection.getPreparedStatement(sql);
    ResultSet rs = ps.executeQuery();
    while (rs.next()) {
        if (result == null) result = new ArrayList<Alumno>();
        result.add(new Alumno(
            rs.getInt("ID_ALUMNO"),
            rs.getString("NOMBRE"),
            rs.getString("APELLIDOS"),
            rs.getString("FEC_NAC"),
            rs.getString("CORREO_ELECTRONICO"),
            rs.getInt("HORAS_FALTAS")
        ));
    }
    rs.close();
    ps.close();
    return result;
}
2. Herramientas ORM: Hibernate y la Especificación JPA

Las herramientas ORM permiten crear una capa de acceso a datos mapeando una clase por cada tabla de la base de datos. Aportan un lenguaje de consultas propio e independiente del SGBD, permitiendo migrar de motor de base de datos con cambios mínimos en el archivo de configuración.

  • Ventajas de los ORM: Reducen el tiempo de desarrollo, abstraen de la base de datos, fomentan la reutilización y portabilidad, producen código más limpio y ofrecen un lenguaje de consulta propio.
  • Principal Inconveniente: Pérdida de control directo sobre el SQL generado; si no se comprende cómo opera el ORM, puede lanzar muchas más consultas de las necesarias.
  • Ejemplos en el mercado: Hibernate y EclipseLink (Java), Doctrine (PHP), NHibernate (C#/.NET), Django ORM y SQLAlchemy (Python).

2.1. Comparativa: JDBC vs. Hibernate

Tecnología Ventajas Desventajas
JDBC Mayor control sobre el SQL, mejor rendimiento general y aprovechamiento total de las funciones específicas del SGBD. Desarrollo y mantenimiento mucho más costosos; alta propensión a errores manuales durante el mapeo.
Hibernate Desarrollo más rápido usando entidades en lugar de consultas SQL, menor código repetitivo y mantenimiento más sencillo. Curva de aprendizaje mayor y rendimiento ligeramente inferior al acceso nativo directo.

2.2. Relación entre JPA (Jakarta Persistence) e Hibernate

JPA (Jakarta Persistence): Es la especificación estándar de Java para la persistencia que independiza la capa de negocio de la de almacenamiento, pero carece de implementación propia. Define tres pilares:

  1. Mecanismos para relacionar objetos Java con el esquema relacional mediante anotaciones o XML.
  2. Una API sencilla para operaciones CRUD a través de jakarta.persistence.EntityManager.
  3. El lenguaje de consultas orientado a objetos JPQL (Java Persistence Query Language).

Hibernate: Es un framework real que implementa en su módulo central (hibernate-core) toda la especificación JPA, añadiendo además capacidades propias como el lenguaje HQL (Hibernate Query Language, que amplía JPQL).

Nota sobre paquetes: Desde Jakarta EE 9 (2020) el paquete oficial es jakarta.persistence. Si un código utiliza javax.persistence corresponde a versiones antiguas (Hibernate 5 o anterior) y no deben mezclarse.

3. Arquitectura de Hibernate y Equivalencias con JPA

Hibernate mapea objetos Java estándar conocidos como POJOs (Plain Old Java Objects). Para interactuar con la base de datos utiliza una Sesión (Session en Hibernate nativo o EntityManager en JPA), que equivale a una conexión JDBC pero mantiene además el contexto de persistencia (una caché de primer nivel con los objetos cargados o guardados en una unidad de trabajo). Crear y destruir sesiones es computacionalmente muy barato.

5. Creación de Entidades JPA y Registro en la Unidad de Persistencia

5.1. Anotaciones Fundamentales de Mapeo en la Entidad

  • @Entity: Declara que la clase es una entidad gestionada por el motor de persistencia.
  • @Table(name = "..."): Especifica el nombre de la tabla física en la base de datos.
  • @Id: Marca el atributo que actuará como clave primaria.
  • @GeneratedValue(strategy = GenerationType.IDENTITY): Delega en la base de datos la generación automática del ID (AUTO_INCREMENT en MySQL).
  • @Column(...): Define las características de la columna asociada al atributo (nombre, longitud, nulabilidad).

Requisito obligatorio: Toda clase entidad de JPA debe importar de jakarta.persistence y contar con un constructor sin argumentos (vacío).

Código: Clase Entidad Usuario.java
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "usuarios")
public class Usuario {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY) // AUTO_INCREMENT en MySQL
    private Long id;

    @Column(name = "nombre", nullable = false, length = 50)
    private String nombre;

    @Column(name = "mensaje", length = 255)
    private String mensaje;

    /** Constructor vacío obligatorio para JPA. */
    protected Usuario() {
    }

    public Usuario(String nombre, String mensaje) {
        this.nombre = nombre;
        this.mensaje = mensaje;
    }
}

5.2. Registro de la Entidad y Control de Logs

Cada nueva clase anotada con @Entity debe registrarse programáticamente en la configuración mediante .managedClass() (equivalente a las antiguas etiquetas <class> de persistence.xml).

Código: Registro en JPAUtil y Reducción de Logs en App.java
// 1. Registro de la entidad en JPAUtil.java
private static EntityManagerFactory crearEntityManagerFactory() {
    PersistenceConfiguration config = new PersistenceConfiguration(UNIDAD_PERSISTENCIA)
        .provider("org.hibernate.jpa.HibernatePersistenceProvider")
        .transactionType(PersistenceUnitTransactionType.RESOURCE_LOCAL)
        // Añadir aquí cada clase @Entity nueva:
        .managedClass(Usuario.class);
    return config.createEntityManagerFactory();
}

// 2. Ajuste de nivel de log en App.java para ocultar mensajes INFO de arranque
private static final Logger LOG_HIBERNATE = Logger.getLogger("org.hibernate");

public static void main(String[] args) {
    LOG_HIBERNATE.setLevel(Level.WARNING); // El SQL se sigue mostrando por consola
}

Entidades, Valores y Ciclo de Vida en JPA e Hibernate

7. Entidades, Valores e Identidad en JPA

Entidad vs. Valor: En JPA, una entidad es una clase del modelo que se almacena en su propia tabla y posee identidad propia (su clave primaria) y un ciclo de vida independiente de otros objetos. Por el contrario, un valor es un dato que pertenece a una entidad, se guarda junto a ella y carece de ciclo de vida propio. Los valores se dividen en tres categorías: tipos básicos, tipos embeddable (embebidos) y tipos colección.

Identidad e Igualdad: En Java, dos referencias tienen la misma identidad si apuntan al mismo objeto en memoria (a == b devuelve true), mientras que son iguales o equivalentes si su estado coincide (a.equals(b)). Dentro de un mismo EntityManager, JPA hace coincidir ambas: si buscamos dos veces el mismo identificador, obtenemos exactamente la misma instancia en memoria.

Código Ejemplo: Garantía de Identidad en el EntityManager
Estudiante a = em.find(Estudiante.class, 1L);
Estudiante b = em.find(Estudiante.class, 1L);
System.out.println(a == b); // true (ambas referencias apuntan al mismo objeto en memoria)
8. Mapeo de Entidades y Estrategias de Clave Primaria

Para que una clase Java sea una entidad persistente válida en JPA debe cumplir los siguientes requisitos:

  • Estar anotada con @Entity y poseer un atributo identificador anotado con @Id.
  • Disponer de un constructor sin argumentos con visibilidad public o protected (puede tener constructores adicionales).
  • Ni la clase ni sus atributos persistentes pueden declararse como final.
  • Sus atributos deben ser private y accesibles mediante métodos getters y setters.
  • Para fijar el nombre de la tabla física independientemente del sistema operativo (Windows convierte a minúsculas en MySQL, mientras que Linux distingue mayúsculas), se emplea @Table(name = "...").

8.1. Tipos Envoltorio y Estrategias de Autogeneración (@GeneratedValue)

Se recomienda utilizar tipos envoltorio como Long o Integer en lugar de tipos primitivos (long, int) para la clave primaria. Un valor null indica inequívocamente que el objeto aún no ha sido guardado en la base de datos, mientras que un primitivo inicializaría a 0, pudiendo confundirse con un identificador real.

Estrategia Funcionamiento y Comportamiento en MySQL
GenerationType.IDENTITY Utiliza una columna autonumérica especial (AUTO_INCREMENT). Es la opción recomendada para MySQL. Como la BD genera el ID al insertar, Hibernate ejecuta el INSERT inmediatamente al invocar persist() sin esperar al commit() (impidiendo agrupar inserciones por lotes).
GenerationType.SEQUENCE Utiliza una secuencia SQL para obtener el ID antes de insertar, permitiendo retrasar el INSERT hasta el commit() y agrupar en lotes. En MySQL (que no usa secuencias nativas) la simula creando una tabla Entidad_SEQ reservando bloques de 50 en 50.
GenerationType.AUTO Hibernate selecciona la estrategia automáticamente. Para identificadores numéricos aplica SEQUENCE (creando la tabla _SEQ en MySQL).
GenerationType.TABLE Emplea una tabla adicional en la base de datos con una fila por cada tipo de entidad para almacenar el siguiente valor disponible.
GenerationType.UUID Genera un identificador único universal. El atributo identificador debe ser de tipo java.util.UUID.
9. Mapeo de Valores, Fechas y Tipos Embebidos

En una entidad, todos los atributos se consideran persistentes por defecto si pertenecen a los tipos soportados: primitivos y sus envoltorios, String, BigInteger, BigDecimal, clases de fecha/hora de java.time, UUID, byte[], enumerados (enum) y clases anotadas con @Embeddable.

Ubicación de las anotaciones: Las anotaciones de mapeo (@Id, @Column, etc.) pueden situarse sobre los atributos o sobre los métodos getter (nunca sobre los setter). La ubicación elegida para @Id marca la estrategia que seguirá Hibernate en toda la clase.

9.1. Propiedades de la Anotación @Column y Tipos de Fecha (java.time)

  • name: Modifica el nombre de la columna en la tabla.
  • nullable: Indica si la columna admite valores NULL (false equivale a campo obligatorio NOT NULL).
  • length: Define la longitud máxima en caracteres para columnas de texto.
  • unique: Crea una restricción UNIQUE impidiendo valores duplicados en esa columna.
  • insertable / updatable: Determinan si la columna se incluye en las sentencias INSERT o UPDATE generadas (por defecto true).
Tipo en Java (java.time) Qué Representa Tipo de Columna en MySQL
LocalDate Fecha sin hora DATE
LocalTime Hora sin fecha TIME
LocalDateTime Fecha y hora DATETIME
Instant Instante exacto en UTC DATETIME

9.2. Tipos Embebidos (@Embeddable, @Embedded y @AttributeOverride)

Cuando interesa agrupar varios atributos en una clase reutilizable (por ejemplo, Direccion) sin crear una tabla separada, se anota la clase componente con @Embeddable y el atributo en la entidad contenedora con @Embedded. Hibernate vuelca las columnas del objeto embebido directamente dentro de la tabla de la entidad principal.

Si una entidad contiene dos atributos del mismo tipo embebido (ej. dirección habitual y dirección de facturación), se produciría un error por duplicidad de columnas ("Column 'via' is duplicated"). Para evitarlo, se renombran las columnas del segundo atributo usando @AttributeOverride.

Código Ejemplo: Clase @Embeddable y Sobrescritura con @AttributeOverride
// 1. Clase componente embebible
@Embeddable
public class Direccion {
    @Column(nullable = false)
    private String via;
    @Column(nullable = false, length = 5)
    private String codigoPostal;
    @Column(nullable = false)
    private String poblacion;
    @Column(nullable = false)
    private String provincia;

    protected Direccion() {}
    // Constructor con parámetros, getters y setters...
}

// 2. Uso en una entidad con dos direcciones distintas
@Entity
@Table(name = "usuarios_sistema")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Embedded
    private Direccion direccion; // Usa las columnas: via, codigoPostal, poblacion, provincia

    @Embedded
    @AttributeOverride(name = "via", column = @Column(name = "via_facturacion"))
    @AttributeOverride(name = "codigoPostal", column = @Column(name = "cp_facturacion", length = 5))
    @AttributeOverride(name = "poblacion", column = @Column(name = "poblacion_facturacion"))
    @AttributeOverride(name = "provincia", column = @Column(name = "provincia_facturacion"))
    private Direccion direccionFacturacion;
}
10. Contexto de Persistencia, Estados del Ciclo de Vida y Operaciones

Cada EntityManager posee un contexto de persistencia que actúa como caché de primer nivel: si se solicita con find() un objeto que ya reside en el contexto, lo devuelve inmediatamente sin lanzar otra consulta SELECT a la base de datos. Al cerrar el EntityManager (em.close()), el contexto desaparece.

10.1. Los Cuatro Estados de una Entidad

Estado Descripción y Comportamiento
Transient (Nueva) Recién instanciada con new. El EntityManager no la conoce, no existe fila en la BD y su id autogenerado es null.
Managed (Gestionada) Asociada al contexto de persistencia activo. Cualquier modificación realizada mediante sus setters es detectada y sincronizada automáticamente con la BD al confirmar la transacción.
Detached (Separada) Posee id y estuvo gestionada previamente, pero su EntityManager se cerró (close()), se limpió (clear()) o se desvinculó con detach(). Sus cambios en memoria no se guardan en la BD.
Removed (Eliminada) Entidad gestionada que ha sido marcada para su eliminación con remove(). El DELETE físico se ejecutará al hacer commit().
Diagrama de Transición de Estados en JPA
                      [ Base de Datos ]
                              │
                         find() (SELECT)
                              ▼
[ No existe ] ──new──► [ TRANSIENT ] ──persist() (INSERT)──► [  MANAGED  ] ◄──setter (UPDATE al confirmar)─┐
                                                              │   ▲   │   └───┐                           │
                                       remove() (DELETE)──────┘   │   │       └───────────────────────────┘
                                              │          persist()│   ├──close() / clear() / detach()──► [ DETACHED ]
                                              ▼                   │   │                                       │
                                         [ REMOVED ] ─────────────┘   └──────merge() (SELECT + UPDATE)────────┘

10.2. Operaciones del EntityManager y Transacciones

  • Guardar (persist(entidad)): Pasa un objeto transient a managed. Solo admite objetos nuevos; si se le pasa un objeto que ya tiene id o está detached lanza el error detached entity passed to persist.
  • Recuperar (find(Clase.class, id) y getReference()): find() busca por clave primaria y devuelve la entidad managed o null si no existe (no requiere transacción porque solo lee). Por su parte, getReference() devuelve un proxy sin consultar la BD hasta que se accede a sus datos, lanzando EntityNotFoundException si no existe.
  • Modificar (Dirty Checking): JPA no tiene método update(). Si el objeto está en estado managed dentro de una transacción, basta con modificar sus atributos mediante sus setters; al hacer commit(), Hibernate compara el estado actual con el original y lanza el UPDATE automáticamente si detecta cambios.
  • Reincorporar (merge(entidadDetached)): Permite guardar los cambios de un objeto detached. Carga o busca en el contexto la entidad con ese id, copia en ella los valores del objeto separado y devuelve una nueva referencia managed. El objeto original pasado como argumento sigue estando detached.
  • Eliminar (remove(entidadManaged)): Marca un objeto managed como removed para lanzar su DELETE al confirmar la transacción. Si se intenta borrar un objeto detached lanza el error Removing a detached instance (para borrar por ID se debe hacer primero find() y luego remove()).
  • Comprobar estado (contains(objeto)): Devuelve true si la instancia se encuentra actualmente gestionada en el contexto de persistencia.
Código Ejemplo: Plantilla Segura de Transacción y Operaciones del Ciclo de Vida
EntityManager em = JPAUtil.getEntityManager();
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();

    // 1. PERSIST: Guardar nuevo objeto (Transient -> Managed)
    Estudiante nuevo = new Estudiante("Ana", "Ruiz");
    em.persist(nuevo); // Con IDENTITY ejecuta INSERT inmediatamente y asigna ID

    // 2. FIND + DIRTY CHECKING: Recuperar y modificar sin llamar a ningún update()
    Estudiante existente = em.find(Estudiante.class, 1L);
    if (existente != null) {
        existente.setNombre("Ana María"); // Al estar Managed, hará UPDATE en el commit
    }

    // 3. MERGE: Guardar cambios de un objeto Detached
    // IMPORTANTE: recoger y usar la referencia devuelta por merge()
    Estudiante gestionado = em.merge(objetoDetached);

    // 4. REMOVE: Buscar primero para asegurar estado Managed y luego eliminar
    Estudiante aBorrar = em.find(Estudiante.class, 3L);
    if (aBorrar != null) {
        em.remove(aBorrar); // Ejecutará DELETE en el commit
    }

    tx.commit();
} catch (RuntimeException ex) {
    if (tx.isActive()) {
        tx.rollback(); // Deshace cambios en la BD (pero no revierte los objetos en memoria)
    }
    System.out.println("Operación cancelada: " + ex.getMessage());
} finally {
    em.close(); // Cierra el contexto; todos los objetos Managed pasan a Detached
}
11. Diagnóstico de Errores del Ciclo de Vida
Error o Síntoma Causa Solución
"detached entity passed to persist" Se invoca persist() sobre un objeto que ya posee id (está detached o se le asignó el id manualmente). Utilizar merge() para objetos existentes, o dejar que el id lo asigne @GeneratedValue en objetos nuevos.
"Removing a detached instance" Se invoca remove() pasándole un objeto perteneciente a un EntityManager que ya fue cerrado. Recuperar primero la entidad en el EntityManager activo mediante find() y pasar esa instancia a remove().
Los cambios no se guardan en la BD y no salta ningún error Se modificó un objeto en estado detached, o se modificó sin abrir y confirmar una transacción (tx.begin() / tx.commit()). Sincronizar con merge() o realizar los cambios con los setters dentro de una transacción activa del EntityManager que cargó la entidad.
Se pierden cambios realizados después de llamar a merge() Se continúa modificando la variable original (que permanece en estado detached) en lugar de la copia devuelta. Asignar y trabajar siempre con la referencia gestionada que retorna el método: entidad = em.merge(entidad);.

Asociaciones entre Entidades en JPA e Hibernate

12. Introducción a las Asociaciones entre Entidades

En los modelos de dominio relacionales, las entidades están conectadas entre sí mediante claves externas (foreign keys), que consisten en la presencia de la clave primaria de una tabla dentro de otra (o en la misma tabla en relaciones reflexivas).

En JPA, una asociación se modela como un atributo cuyo tipo es otra entidad o una colección de entidades, pudiendo configurarse de forma unidireccional (navegable solo desde un extremo) o bidireccional (navegable desde ambos extremos).

13. Asociación Many-To-One (Muchos a Uno) y @JoinColumn

Es la asociación más habitual y representa una relación padre/hijo donde el lado muchos es el hijo y el lado uno es el padre (sin confundirse con herencia). En su versión unidireccional, la asociación se define únicamente en el lado muchos mediante @ManyToOne.

13.1. Propiedades de @JoinColumn y @ForeignKey

Propiedad Función y Comportamiento
name Especifica el nombre de la columna clave externa en la tabla (ej. persona_id).
foreignKey Permite nombrar la restricción de clave externa mediante @ForeignKey(name = "fk_...") o desactivarla con ConstraintMode.NO_CONSTRAINT.
referencedColumnName Indica la columna destino del JOIN (por defecto JPA asume la clave primaria de la entidad objetivo).
nullable / unique Añaden restricciones NOT NULL (default true) o UNIQUE (default false) sobre la columna clave externa.
insertable / updatable Indican si la columna participa en INSERT y UPDATE (default true). Se establecen a false si la misma columna está mapeada dos veces en la entidad (como atributo escalar y como asociación) para evitar el error de columna duplicada.
columnDefinition / table Definen el fragmento SQL exacto de creación de columna o la tabla específica donde realizar el JOIN.
Código Ejemplo: Asociación @ManyToOne Unidireccional (Telefono → Persona)
@Entity
@Table(name = "personas")
public class Persona {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String nombre;

    protected Persona() {}
    public Persona(String nombre) { this.nombre = nombre; }
    // getters y setters...
}

@Entity
@Table(name = "telefonos")
public class Telefono {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String numero;

    @ManyToOne
    @JoinColumn(name = "persona_id", foreignKey = @ForeignKey(name = "fk_telefono_persona"))

// Uso: persistir primero el lado padre ("uno") y después el hijo ("muchos")
Persona pepe = new Persona("Pepe");
Telefono telefono = new Telefono("924000000");
telefono.setPersona(pepe);
em.persist(pepe);
em.persist(telefono); // Ejecuta INSERT con persona_id = id de Pepe
14. Asociación One-To-Many (Uno a Muchos)

Enlaza la entidad padre con una colección de entidades hijas. Puede implementarse de forma unidireccional o bidireccional, existiendo diferencias importantes en el esquema relacional generado y en su eficiencia.

14.1. One-To-Many Unidireccional vs. Bidireccional

Modalidad Esquema Generado en BD Sincronización y Eficiencia
Unidireccional
@OneToMany solo en el padre		 Crea 3 tablas: padre, hija y una tabla intermedia (ej. personas_telefonos) con restricción UNIQUE en el ID del hijo. Se gestiona añadiendo elementos directamente a la lista del padre. Quitar un hijo requiere borrar una fila de la tabla intermedia.
Bidireccional
@OneToMany(mappedBy) en padre + @ManyToOne en hijo		 Crea solo 2 tablas: la clave externa reside en la tabla hija (el lado propietario). Sin tabla intermedia. Más eficiente (quitar un hijo es un simple UPDATE a NULL o un DELETE con orphanRemoval). Requiere métodos auxiliares (addX / removeX) para sincronizar ambos lados.

Atributos clave de @OneToMany: cascade = CascadeType.ALL propaga las operaciones del padre (guardar, borrar) a sus hijos, y orphanRemoval = true elimina automáticamente de la base de datos cualquier hijo que sea retirado de la colección del padre.

Código Ejemplo: @OneToMany Bidireccional con Métodos de Sincronización
// LADO INVERSO (Padre)
@Entity
@Table(name = "personas")
public class PersonaBidireccional {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String nombre;

    @OneToMany(mappedBy = "persona", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<TelefonoBidireccional> telefonos = new ArrayList<>();

    protected PersonaBidireccional() {}
    public PersonaBidireccional(String nombre) { this.nombre = nombre; }

    // Métodos auxiliares obligatorios para mantener ambos lados sincronizados
    public void addTelefono(TelefonoBidireccional telefono) {
        telefonos.add(telefono);
        telefono.setPersona(this); // Actualiza el lado propietario
    }

    public void removeTelefono(TelefonoBidireccional telefono) {
        telefonos.remove(telefono);
        telefono.setPersona(null);
    }
}

// LADO PROPIETARIO (Hijo: contiene la clave externa en BD)
@Entity
@Table(name = "telefonos")
public class TelefonoBidireccional {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String numero;

    @ManyToOne
    @JoinColumn(name = "persona_id")
    private PersonaBidireccional persona;

    protected TelefonoBidireccional() {}
    public TelefonoBidireccional(String numero) { this.numero = numero; }
    public void setPersona(PersonaBidireccional persona) { this.persona = persona; }
}
15. Asociación One-To-One (Uno a Uno)

Asocia una única instancia de una entidad con una única instancia de otra. En la variante unidireccional, la clave externa con restricción de unicidad (UQ) reside en la entidad que declara @OneToOne y @JoinColumn. En la variante bidireccional, es recomendable situar la clave externa en la entidad dependiente (lado propietario) y usar mappedBy en la entidad principal.

Código Ejemplo: @OneToOne Bidireccional (TelefonoOneBi ↔ DetallesTelefonoBi)
// LADO INVERSO (Principal)
@Entity
@Table(name = "telefonos")
public class TelefonoOneBi {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String numero;

    @OneToOne(mappedBy = "telefono", cascade = CascadeType.ALL, orphanRemoval = true)
    private DetallesTelefonoBi detalles;

    protected TelefonoOneBi() {}
    public TelefonoOneBi(String numero) { this.numero = numero; }

    public void addDetalles(DetallesTelefonoBi detalles) {
        detalles.setTelefono(this);
        this.detalles = detalles;
    }

    public void removeDetalles() {
        if (detalles != null) {
            detalles.setTelefono(null);
            this.detalles = null;
        }
    }
}

// LADO PROPIETARIO (Dependiente: aloja la FK telefono_id con restricción UNIQUE)
@Entity
@Table(name = "detalles_telefono")
public class DetallesTelefonoBi {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String proveedor;
    private String tecnologia;

    @OneToOne
    @JoinColumn(name = "telefono_id")
    private TelefonoOneBi telefono;

    protected DetallesTelefonoBi() {}
    public DetallesTelefonoBi(String proveedor, String tecnologia) {
        this.proveedor = proveedor;
        this.tecnologia = tecnologia;
    }
    public void setTelefono(TelefonoOneBi telefono) { this.telefono = telefono; }
}
16. Asociación Many-To-Many (Muchos a Muchos)

Modela relaciones donde múltiples registros de una tabla se vinculan con múltiples registros de otra (ej. Libro y Autor). A nivel físico requiere una tabla intermedia con dos claves externas. El lado propietario define dicha tabla con @JoinTable, mientras que el lado inverso utiliza mappedBy.

  • Uso de Set en lugar de List: Evita duplicados en la colección (un mismo autor no debe figurar dos veces en el mismo libro).
  • Precaución con CascadeType: Nunca se debe aplicar CascadeType.REMOVE ni CascadeType.ALL en una relación @ManyToMany, ya que borrar un libro eliminaría también a sus autores aunque tengan otros libros asociados.
  • Tablas intermedias con atributos propios: Si la relación necesita guardar datos adicionales (ej. orden de firma de autores), la tabla intermedia debe transformarse en una entidad intermedia con dos relaciones @ManyToOne.
  • ¿Unidireccional o bidireccional?: Solo conviene implementar bidireccionalidad cuando se vaya a navegar frecuentemente en ambos sentidos; si no, es preferible mantenerla unidireccional o resolver el lado inverso mediante consultas JPQL.
Código Ejemplo: @ManyToMany Bidireccional (Libro ↔ Autor)
// LADO PROPIETARIO (Define la tabla intermedia con @JoinTable)
@Entity
@Table(name = "libros")
public class Libro {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String titulo;

    @ManyToMany
    @JoinTable(
        name = "libro_autor",
        joinColumns = @JoinColumn(name = "libro_id"),
        inverseJoinColumns = @JoinColumn(name = "autor_id")
    )
    private Set<Autor> autores = new HashSet<>();

    protected Libro() {}
    public Libro(String titulo) { this.titulo = titulo; }

    public void addAutor(Autor autor) {
        autores.add(autor);
        autor.getLibros().add(this);
    }

    public void removeAutor(Autor autor) {
        autores.remove(autor);
        autor.getLibros().remove(this);
    }
}

// LADO INVERSO
@Entity
@Table(name = "autores")
public class Autor {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String nombre;

    @ManyToMany(mappedBy = "autores")
    private Set<Libro> libros = new HashSet<>();

    protected Autor() {}
    public Autor(String nombre) { this.nombre = nombre; }
    public Set<Libro> getLibros() { return libros; }
}
17. Diagnóstico de Errores Frecuentes en Asociaciones
Error o Síntoma Causa Solución
"failed to lazily initialize a collection ... no Session" Se intenta recorrer una colección (@OneToMany o @ManyToMany) con carga perezosa (Lazy) después de haber cerrado el EntityManager. Acceder y procesar la colección mientras el EntityManager sigue abierto.
TransientPropertyValueException
("references an unsaved transient instance")		 Se intenta guardar una entidad hija cuya entidad padre asociada aún está en estado transient (no guardada en BD). Persistir primero la entidad padre antes que la hija, o configurar propagación en cascada desde el padre.
La clave externa queda a NULL y no se produce ningún error En una asociación bidireccional solo se actualizó la colección del lado inverso (mappedBy) sin asignar el lado propietario. Utilizar siempre los métodos auxiliares que sincronizan ambos extremos (addTelefono(), addAutor()).
"Column 'persona_id' is duplicated in mapping for entity" La misma columna física está mapeada dos veces en la entidad (como atributo escalar y como relación). Configurar insertable = false, updatable = false en una de las dos declaraciones.
Se eliminan entidades relacionadas que no debían borrarse Uso indebido de cascade = CascadeType.ALL o REMOVE en una relación @ManyToMany o en el extremo @ManyToOne. Limitar la cascada de borrado únicamente del padre hacia sus hijos dependientes (@OneToMany / @OneToOne).

Generación Automática de Entidades: Ingeniería Inversa con Hibernate (hbm2java)

18. Ingeniería Inversa en Hibernate (hbm2java)

Enfoque inverso: A diferencia del desarrollo dirigido por el modelo (donde escribimos las entidades Java y Hibernate genera las tablas con drop-and-create), la ingeniería inversa parte de una base de datos relacional ya existente para generar automáticamente las clases @Entity correspondientes.

Cuándo utilizarla: Resulta especialmente útil cuando la base de datos ya contiene datos en producción, ha sido diseñada por especialistas en SQL aprovechando características avanzadas del SGBD, o consta de un elevado número de tablas cuya codificación manual sería tediosa y propensa a errores.

La herramienta hbm2java: Es un objetivo (goal) integrado en el plugin oficial de Maven hibernate-maven-plugin. Al ejecutarse mediante Maven, no requiere instalar extensiones adicionales ni depende del IDE utilizado (funciona igual en Eclipse, IntelliJ IDEA, NetBeans, VS Code o terminal).

Flujo de Trabajo de Generación Automática (hbm2java)
[1. Base de Datos (ej. ra3_videojuegos)] ──┐
[2. reveng/conexion.properties]         ──┼──► [4. Objetivo Maven: hbm2java]
[3. reveng/hibernate-reverse-engineering.xml]┘               │
                                                             ▼
[6. Revisar y corregir] ◄──(copiar a mano)── [5. target/generated-sources/...]
(Many-To-Many, catalog, formato)             ──► [ src/main/java/... ]
19. Configuración de Maven y Ficheros de Ingeniería Inversa

Los archivos utilizados por el generador se alojan habitualmente en una carpeta específica del proyecto (ej. reveng/) para mantenerlos separados de los recursos de ejecución de la aplicación (src/main/resources).

19.1. Declaración del Plugin en pom.xml

Configuración de hibernate-maven-plugin en pom.xml
<build>
    <plugins>
        <plugin>
            <groupId>org.hibernate.orm</groupId>
            <artifactId>hibernate-maven-plugin</artifactId>
            <version>${hibernate.version}</version>
            <configuration>
                <propertyFile>${project.basedir}/reveng/conexion.properties</propertyFile>
                <revengFile>${project.basedir}/reveng/hibernate-reverse-engineering.xml</revengFile>
            </configuration>
        </plugin>
    </plugins>
</build>

19.2. Fichero reveng/conexion.properties

Define los parámetros JDBC de acceso al esquema que se va a inspeccionar. Es fundamental especificar hibernate.default_catalog con el nombre exacto de la base de datos: sin esta propiedad, el generador podría mezclar tablas homónimas de otras bases de datos del servidor (generando atributos duplicados) y añadiría el atributo catalog="..." en todas las anotaciones @Table.

Contenido de reveng/conexion.properties
hibernate.connection.driver_class=com.mysql.cj.jdbc.Driver
hibernate.connection.url=jdbc:mysql://localhost:3306/ra3_videojuegos
hibernate.connection.username=root
hibernate.connection.password=
hibernate.default_catalog=ra3_videojuegos

19.3. Personalización en reveng/hibernate-reverse-engineering.xml

Este archivo XML controla la conversión de tipos de datos, el filtrado de tablas, el paquete de destino y el renombrado de las clases resultantes:

  • <type-mapping>: Establece la correspondencia entre tipos SQL y tipos Java. Sin este bloque, las columnas NOT NULL se generarían como tipos primitivos (int, long, double) y las fechas como java.util.Date en lugar de Long, Integer, Double y java.time.LocalDate.
  • <table-filter>: Filtra qué tablas se procesan y asigna el paquete Java destino. Los tres atributos match-catalog, match-schema y match-name son obligatorios (".*" indica cualquiera); omitir alguno provoca un NullPointerException.
  • <table>: Asigna nombres de clase en singular (ej. Videojuego) a tablas nombradas en plural en la BD (ej. videojuegos).
Ejemplo Completo de reveng/hibernate-reverse-engineering.xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE hibernate-reverse-engineering PUBLIC
  "-//Hibernate/Hibernate Reverse Engineering DTD 3.0//EN"
  "http://hibernate.org/dtd/hibernate-reverse-engineering-3.0.dtd">

<hibernate-reverse-engineering>
    <!-- 1. Mapeo de tipos SQL a tipos envoltorio y java.time -->
    <type-mapping>
        <sql-type jdbc-type="BIGINT"  hibernate-type="java.lang.Long"/>
        <sql-type jdbc-type="INTEGER" hibernate-type="java.lang.Integer"/>
        <sql-type jdbc-type="DOUBLE"  hibernate-type="java.lang.Double"/>
        <sql-type jdbc-type="DATE"    hibernate-type="java.time.LocalDate"/>
    </type-mapping>

    <!-- 2. Filtro de tablas y paquete destino (los 3 match-* son obligatorios) -->
    <table-filter match-catalog=".*" match-schema=".*" match-name=".*"
                  package="com.iesvjp.orm.modelo"/>

    <!-- 3. Renombrado de tablas en plural a clases en singular -->
    <table name="estudios_desarrollo" class="com.iesvjp.orm.modelo.EstudioDesarrollo"/>
    <table name="videojuegos"         class="com.iesvjp.orm.modelo.Videojuego"/>
    <table name="plataformas"         class="com.iesvjp.orm.modelo.Plataforma"/>
</hibernate-reverse-engineering>
20. Ejecución del Objetivo Maven y Revisión Manual

Ejecución: Tras crear la base de datos en MySQL, se lanza el objetivo Maven org.hibernate.orm:hibernate-maven-plugin:hbm2java (en Eclipse: Run As → Maven build... y escribir el goal; en terminal: mvn org.hibernate.orm:hibernate-maven-plugin:hbm2java).

Copia manual a src/main/java: Las clases se generan en target/generated-sources/... y deben copiarse manualmente a src/main/java/.... Se generan en target/ de forma intencionada para que una futura reejecución del generador no sobrescriba las correcciones manuales aplicadas en el código fuente del proyecto.

20.1. Particularidades y Corrección Obligatoria de Many-To-Many

  • Anotaciones en los getters: El generador sitúa las anotaciones JPA sobre los métodos getXXX() en lugar de los atributos (Hibernate lo soporta de forma equivalente).
  • Características adicionales: Implementan Serializable, incluyen carga FetchType.LAZY en asociaciones, generan tres constructores (vacío, campos obligatorios y completo) y carecen de métodos auxiliares addX() / removeX(). Las relaciones @ManyToOne y @OneToMany y las tablas intermedias puras se detectan correctamente.
  • Corrección crítica en @ManyToMany: El generador configura ambos extremos como lados propietarios (ambos incluyen @JoinTable y ninguno tiene mappedBy). Si se guardan datos actualizando los dos lados, Hibernate intentará insertar la fila intermedia dos veces provocando un error de clave duplicada. Se debe dejar @JoinTable en un único lado propietario (ej. Videojuego) y sustituirlo por mappedBy en el lado inverso (ej. Plataforma).
Código Ejemplo: Corrección de @ManyToMany en el Lado Inverso (Plataforma.java)
// ANTES (Generado por hbm2java — INCORRECTO: dos lados propietarios)
@ManyToMany(fetch = FetchType.LAZY)
@JoinTable(name = "videojuego_plataforma", catalog = "ra3_videojuegos",
    joinColumns = { @JoinColumn(name = "plataforma_id", nullable = false, updatable = false) },
    inverseJoinColumns = { @JoinColumn(name = "videojuego_id", nullable = false, updatable = false) })
public Set<Videojuego> getVideojuegos() {
    return this.videojuegos;
}

// DESPUÉS (Corregido — Lado inverso referenciando al atributo propietario)
@ManyToMany(fetch = FetchType.LAZY, mappedBy = "plataformas")
public Set<Videojuego> getVideojuegos() {
    return this.videojuegos;
}
